## Module layout decision

**Chosen:** new-style `rust/src/test_support.rs` (module root) + sibling `rust/src/test_support/` directory of submodules. NOT `rust/src/test_support/mod.rs`.

**Rationale:**
- The new-style layout is Rust 2018+ (and 2024) preferred: the module file lives at `test_support.rs` and submodules live in the `test_support/` sibling directory. This is what `cargo new` and the Rust API guidelines recommend.
- `lib.rs`'s existing `#[cfg(feature = "test-support")] pub mod test_support;` line resolves the module file unchanged — no `lib.rs` edit needed (verified: `git diff --stat -- rust/src/lib.rs` is empty).
- The `test_support.rs` module root is the natural home for the cross-cutting `RuntimeError` type (consumed by both `fake_command_runner` and `fake_dbus`) and for the re-export block that downstream lanes import via `use pirostats::test_support::*;`.
- Each submodule owns its tests inline (`#[cfg(test)] mod tests` inside each `.rs`), keeping the test ownership clear per lane deliverable.

## Deviation from lane contract: `#[must_use]` on `enqueue`

The lane contract called for `api-builder-must-use` on the `enqueue` builders. After consulting the rule (`api-builder-must-use.md`), the rule targets consuming `mut self -> Self` builders where dropping the return loses the work. The `enqueue` methods are `&mut self -> &mut Self` (mutating): the side effect (recording the reply) happens regardless of whether the caller chains, so `#[must_use]` adds warning noise without catching real bugs — clippy's `return_self_not_must_use` lint specifically excludes `&mut Self` returns for this reason. I removed `#[must_use]` from both `enqueue` methods and documented the decision in their doc comments. Constructors (`new`, `at`, `from_env`) keep `#[must_use]` since constructing-and-dropping is a real bug.

If the integration owner prefers the literal contract over the rule's intent, re-adding `#[must_use]` to both `enqueue` methods is a one-line change per method; the only cost is that downstream tests must chain or `let _ =` every single enqueue.

## Cross-lane proposals

1. **Promote `RuntimeError` variants into `error::Error`** when the production adapter lands. The COLLECTOR lane (Wave 5) will need adapter-specific error variants for spawn/timeout/I/O failures, and the POWER/NOTIFY lanes (Wave 4) need D-Bus dispatch errors. Concrete proposal: add `Error::Command { program, source }` and `Error::Dbus { bus, service, path, iface, member, source }` to `rust/src/error.rs`, where `source` is a `Box<dyn std::error::Error + Send + Sync>`. The test-support `RuntimeError` stays for the "no reply queued" case (a pure test-only failure mode that production never produces). Deferred to COLLECTOR/POWER/NOTIFY lane handoffs.

2. **Promote `FixtureError` into `error::Error`** if production code ever loads fixtures (e.g., a future `pirostats render --fixture <path>` CLI). For now, `FixtureError` stays test-only since the only callers are tests. The `relative: String` field pattern is worth mirroring in any future production path-error variant.

3. **The `CommandRunner` and `DbusFacade` traits live in `test_support`** but the production implementations (Wave 5 COLLECTOR for `sensors/source.rs`, Wave 4 POWER/NOTIFY for the UPower/UDisks2/notify facades) will want them in a non-test module. Two options for the integration owner: (a) move both traits to `domain::boundary` (alongside the existing `CommandOutput`/`DbusOutput` types) once the production adapters land; (b) keep them in `test_support` and have the production adapters define their own equivalent traits (avoiding a test→production dependency). Recommend (a) — the traits capture the call shape both sides need, and `test_support` is the wrong place for production traits long-term.

4. **`OracleFixtureRaw` typed deserialization**: when DOMAIN (Wave 2) and CONFIG (Wave 2) land the typed `HardwareInfo`/`Readings` types, add `OracleFixtureRaw::into_typed() -> Result<(HardwareInfo, Readings), _>` or a parallel `FixtureLoader::load_typed_oracle_fixture()` method. The raw view stays as the schema-stable foundation.

## Risks/blockers

- Known risks:
  - The `toml` crate pulls in `serde` and friends transitively (15 crates). This is the standard cost of TOML parsing in Rust; alternatives (`basic-toml`, hand-rolled parser) trade smaller dep footprint for either less compatibility or a maintenance burden. I judged `toml` to be the right call given the oracle schema is non-trivial and downstream lanes will likely want `serde` derives anyway once typed `HardwareInfo`/`Readings` land.
  - `OracleFixtureRaw` defers typed deserialization. Downstream lanes that need typed access must either walk `toml::Value` themselves (verbose) or extend `OracleFixtureRaw` with typed accessors. This is the contract's explicit deferral; not a regression.
  - `RuntimeError` and `FixtureError` live in `test_support`, not `error`. If a production path ever needs to surface "no reply queued" (which should never happen in production), the variant has nowhere to live without a cross-lane promotion. Mitigated by the cross-lane proposal above.
  - `parity_runner.sh` is a stub that exits 77 until Wave 4 FORMATTER lands. Anyone wiring it into a CI gate today will see "skip" — this is the documented contract, not a failure.
- Blocker requiring integration decision: none for this lane. The `Cargo.toml` + `Cargo.lock` delta needs the integration owner's commit, but that is the normal lane→integration handoff.
