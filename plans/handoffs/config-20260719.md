## Dependencies and safety

- **New dependency: `serde = { version = "1", features = ["derive"] }`**.
  - **Why over stdlib**: derive-based `Deserialize` for the typed `Config` tree. Each leaf struct uses `#[serde(default)]` at the container level, which fills missing fields from the struct's own `Default` impl — the exact behavior of Python's `_from_dict` (ignore unknown keys, fall back to dataclass defaults). Hand-writing this for ~14 structs would have been hundreds of lines of fragile match-on-toml::Value; the derive is 1 attribute per struct.
  - **License**: MIT OR Apache-2.0. GPL-2.0-or-later compatible.
  - **Native/build/runtime**: pure-Rust, no native code, no build script, no proc-macro of its own (`serde_derive` is the proc-macro and is already vendored transitively via `toml`). The `Cargo.lock` diff is +11 lines: the `serde` facade crate proper (which re-exports `serde_core` + wires `serde_derive`); the underlying `serde_core` / `serde_derive` / `syn` / `quote` / `proc-macro2` / `unicode-ident` were already in the lock.
  - **Transitive footprint** (`cargo tree -i serde`):
    ```
    serde v1.0.229
    ├── serde_core v1.0.229 (already vendored)
    └── serde_derive v1.0.229 (already vendored, proc-macro)
    ```
    Zero new transitive runtime crates.
  - **Arch packaging impact**: pure-Rust, vendored by cargo; no system library added.
  - **Replacement cost / lockfile pin**: `Cargo.lock` pins `serde v1.0.229`. The version constraint `1` allows semver-compatible upgrades; the lock prevents drift. To replace: remove the `serde` line from `Cargo.toml`, switch the `Deserialize` derives to a hand-written match-on-`toml::Value` per struct (or another serde-like crate).

## Risks/blockers

- **Known risks**:
  - **`Path::exists()` TOCTOU in `default_config_path` / `resolve_style`**: same as Python; the daemon hot-reloads on file events so a stale result self-heals on the next reload. Low risk.
  - **`detect_machine` host coupling**: the integration test `default_config_has_no_unknown_items` and `tests/config_default_load.rs::*` call `load_config(None, …)`, which reads `/sys/class/dmi/id/*`. On a CI host without DMI access (container, some VMs), `detect_machine` returns `None` — which is the expected behavior and what the tests assert (`cfg.machine == ""`). If a CI host happens to match a real machine block in the shipped `machines.toml` (which has none today), the test would catch the regression.
  - **`XDG_CONFIG_HOME` env coupling in tests**: the integration test calls `load_config(None, …)` which calls `default_config_path()`, which checks `$XDG_CONFIG_HOME/pirostats/config.toml`. If a CI runner has a real user config there, the test would load THAT instead of the shipped default. The shipped default is the contract; the test asserts the shipped fields, so a user override would fail the test loudly. Acceptable: this surfaces real divergence rather than hiding it. Mitigation if it ever flakes: the integration test could `setenv("XDG_CONFIG_HOME", "/nonexistent")` under a binary-wide mutex (matching the runtime tests' pattern).
  - **`/tmp` fixture cleanup**: tests write PID-unique temp files under `std::env::temp_dir()` and remove them on success. A panic mid-test leaks the file; the PID-unique naming prevents collisions across runs. Not committed regardless.
  - **`toml::Table` insertion order**: `parse_kde_ini` returns a `BTreeMap<String, BTreeMap<String, String>>` (sorted by header), while Python iterates a dict in insertion order. The Python code returns the FIRST matching applet root; if multiple applet roots existed (which they shouldn't — one PiroStats applet per containment), iteration order could differ. Documented; low risk.
- **Blocker requiring integration decision**: none. The slice is self-contained and validates cleanly.
- **Suggested next lane/API changes** (proposals, not made opportunistically):
