## Dependencies and safety

- **New dependency: `nix = "0.29"`** (features: `fs`, `process`, `user`; `default-features = false`).
  - **Why over stdlib**: `std` does not expose `flock(2)` (needed for `step_page` serialization) or `getuid(2)` (needed for the `/tmp/pirostats-{uid}` fallback). Both require a syscall.
  - **Why `nix` over `libc` + scoped `unsafe`**: `nix` provides safe wrappers (`nix::fcntl::Flock`, `nix::unistd::getuid`) so the crate-level `#![deny(unsafe_code)]` stays in effect everywhere with zero `unsafe` blocks in production code. `libc` would require a module-level `#[allow(unsafe_code)]` on `runtime/page.rs` plus disciplined `unsafe { ... }` blocks for every `flock`/`getuid` call, expanding the unsafe-policy audit surface for no functional gain. The lane contract's recommendation (`nix`) is followed.
  - **License**: MIT. GPL-2.0-or-later compatible.
  - **Native/build/runtime**: pure-Rust bindings over `libc`; no native code, no build script, no proc-macro. The `cfg_aliases` build-dependency is a tiny zero-code-gen helper.
  - **Transitive footprint** (`cargo tree`):
    ```
    nix v0.29.0
    ├── bitflags v2.13.1
    ├── cfg-if v1.0.4
    └── libc v0.2.186
    [build-dependencies]
    └── cfg_aliases v0.2.2
    ```
    Four runtime crates + one build-time crate, all permissively licensed (MIT/Apache-2.0/MIT/MIT), all well-maintained Rust-ecosystem staples.
  - **Arch packaging impact**: `nix`, `libc`, `bitflags`, `cfg-if` are pure-Rust and vendored by cargo; no system library required. No `pacman` dependency added.
  - **Replacement cost / lockfile pin**: `Cargo.lock` pins `nix v0.29.0` and transitive deps. The version constraint `0.29` allows semver-compatible upgrades; the lock prevents drift. To replace: remove the `nix` line from `Cargo.toml`, delete the `runtime/page.rs` flock code, and either drop `step_page` or reimplement with `libc` + `unsafe`.
  - **Features kept/trimmed**: `default-features = false` + `["fs", "process", "user"]`. The `fs` feature provides `Flock`; `user` provides `getuid`; `process` is included for future `getpid`-style needs (not currently used — could be dropped to slim the build, but kept for symmetry with the daemon lane's likely needs). **Trim opportunity for integration owner**: drop `process` if unused after Wave 5 wiring.

Rationale: `std::env::set_var`/`remove_var` became `unsafe` in Rust 2024 edition because env mutation is not thread-safe. The tests serialize every mutation plus the dependent read behind a binary-wide `static ENV_GUARD: Mutex<()>`; worker threads are spawned only while the env is stable and join before `Drop` mutates env again. Integration test binaries are separate processes, so cross-binary env races are impossible. The `// SAFETY:` comments document this contract at each call site.
  - **`nix` internal `unsafe`**: lives inside the `nix` crate (out of our audit scope); `nix` is a widely-reviewed safe-wrapper crate. No manual `Send`/`Sync` impls, no `extern` blocks, no `#[no_mangle]` in our code.

## Risks/blockers

- **Known risks**:
  - **Tmp name deviation for HTML publication**: `write_atomic` uses PID-qualified tmp names universally. Python's daemon uses fixed `panel.tmp`/`tooltip.tmp`. The deviation is functionally equivalent (atomic rename-over) and the applet's `nameFilters` should still hide the PID-qualified names (they end in `.tmp`). **Mitigation**: the daemon lane (Wave 5) verifies the applet's `FolderListModel.nameFilters` glob matches `*.tmp` (not a stricter pattern); if it doesn't, add a `write_atomic_fixed_tmp` variant. Low risk.
  - **`target/` collision**: none encountered. The lane ran a single cargo invocation at a time against the default `rust/target/`. If the integration owner runs this lane's tests in parallel with another lane's, `--target-dir rust/target-p2-runtime` isolates (per lane contract's allowance). Not committed regardless.
  - **`Flock` error variant shape**: `nix::fcntl::Flock::lock` returns `Result<Flock<T>, (T, Errno)>` on failure (it hands back the original file so the caller can decide to drop or retry). The `runtime::page::step_page` code drops the returned file and surfaces only the `Errno` as an `io::Error`. This matches the "lock acquisition failed" semantics; a future caller that wants to retry would need the file back, but `step_page` doesn't retry.
  - **Permission tests under root**: the readonly-dir tests (`set_page_returns_err_when_state_dir_is_readonly`, `write_atomic_preserves_target_and_cleans_tmp_on_failure`) rely on the test process not being root (root bypasses Unix permission checks). Running the suite as root would make these tests pass trivially without exercising the error path. **Mitigation**: documented in test comments; CI should run as non-root.
  - **Concurrency test determinism**: `step_page_never_drops_a_notch_under_concurrency` spawns 32 threads and asserts the counter advanced by exactly 32 (mod npages). Without flock this would race and lose updates; with flock it's deterministic. Verified stable across 5 consecutive runs. The test does NOT prove the flock is held (that would require removing the flock and observing failure — a negative test we deliberately avoid committing). The flock's correctness is established by code review of `step_page` + the `nix::fcntl::Flock` RAII contract.
- **Blocker requiring integration decision**: none. The slice is self-contained and validates cleanly.
- **Suggested next lane/API changes** (proposals, not made opportunistically):
  1. **`domain::boundary::FilesystemRoots` integration**: `FilesystemRoots::runtime_root: Option<PathBuf>` exists but `runtime::runtime_dir()` ignores it (reads env directly, matching Python). Proposal: add a `runtime::runtime_dir_under(root: Option<&Path>) -> PathBuf` that takes an explicit root override, used by the daemon lane when it has a resolved `FilesystemRoots`. The env-reading `runtime_dir()` stays as the default for the `page` command (which has no config-loaded root). Defer to integration owner.
  2. **`Error::Runtime` variant**: the top-level `Error` enum (`rust/src/error.rs`) has no `Runtime` variant. Runtime functions currently return `std::io::Result`. Proposal: add `Error::Runtime { context: &'static str, source: io::Error }` so the daemon/CLI lanes can surface runtime failures with the same context-rich display as `Error::Cli`. Defer to integration owner; do NOT edit `error.rs` from this lane.
  3. **`cli::PageDirection` ↔ `runtime::page::PageDirection` bridge**: the CLI already parses `cli::PageDirection { Next, Prev }` (see `cli.rs:130`); `lib.rs` does not re-export it. The `runtime::page::PageDirection` is a separate local enum. Proposal: either (a) re-export `cli::PageDirection` from `lib.rs` and have `runtime::page` use it (creates a runtime→cli dependency — layering violation per the lane contract), or (b) add a `From<cli::PageDirection> for runtime::page::PageDirection` impl in the `DAEMON-CLI` lane (Wave 5), or (c) move `PageDirection` to a neutral module (`domain`?). Recommend (b): the conversion is a one-liner in the composition root. Defer to integration owner.
